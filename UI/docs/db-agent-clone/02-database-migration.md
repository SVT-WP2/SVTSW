# 02. Database: first migration and MikroORM mapping

The clone takes over an existing database whose schema is documented in
[DbAgent/docs/03-database-schema.md](../../../DbAgent/docs/03-database-schema.md). This note
says what the first migration must contain and how the schema maps onto MikroORM. It assumes
MikroORM 6 with the PostgreSQL driver and the migrations package, as in the rentaly project.

## 1. Baseline from the live database, not from the files

Production and dev do not share a schema
([03 §5](../../../DbAgent/docs/03-database-schema.md#5-where-dump-doc-and-code-disagree)): prod is
the June layout plus the Module tables and the `arriveDate` rename; dev additionally has the
September `SvtTestList` changes that the code on `master` requires. Migration 0 is therefore the
**prod** schema, taken from `Dev/db-example/2026-11-08-backup_prod.dump`:

```bash
pg_restore --schema-only --no-owner --no-privileges -f migration0.sql Dev/db-example/2026-11-08-backup_prod.dump
```

committed as the initial migration (raw SQL via `this.addSql(...)`, exactly like rentaly's first
migration), and migration 1 brings prod up to the dev layout (§2). The entities are written to
match the state after migration 1, and `mikro-orm schema:update --dump` must produce an empty diff
against a database at that state before any further migration is written. Dev itself needs only
migration 1's idempotent parts applied, or a fresh restore of the prod dump followed by both
migrations.

## 2. What migration 1 adds

First the September changes that dev already has and prod lacks (these are what `master`'s test
handlers need, so they also unblock the current C++ agent in prod):

| Change | Status |
|---|---|
| Rename `SvtTestList.createsAt` → `createdAt` | dev has it |
| Create enums `dutEntityName` (`Asic`, `Chip`, `ChipBlock`) and `testResultStatus` (`SUCCESS`, `PARTIAL_SUCCESS`, `FAILURE`, `ERROR`) | dev has them |
| Create `SvtTestListToEntityName(testId FK, dutEntityName)` with PK `(dutEntityName, testId)` and `SvtTestListToEntityId(testId FK, dutId)` | dev has them |
| `SvtTestList.testSetupConfigId` NOT NULL + FK → `SvtTestSetupConfig`; `testResultStatus` → enum | dev has them |

| `configBody`: keep `json` (prod) and convert dev's `text` columns, or the reverse; decide (S10) | differs |

Then the changes the clone needs:

| Change | Why | Visible to the running C++ agent? |
|---|---|---|
| `id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` on `WaferLocation`, `ChipLocation`, `EquipmentLocation`, `WaferLoadedInMachine`, `ProbeCardInstalledInMachine` (and `ModuleLocation`, `SvtTestListToEntityId` if they exist) | MikroORM needs a primary key per entity; also gives history rows a stable order ([03 §4](../../../DbAgent/docs/03-database-schema.md#4-tables-without-a-primary-key)) | No: it never names `id` on these tables. | June-dump leftovers (**migration 3**, 2026-11-09): `ProbeCard.arrivalDate` → `arriveDate`, `pcModel` and `pcName` values (S1, S8, S9) | a developer database restored from the June 2026 dump still had them; migration 0 adds what is missing but cannot rename | No: guarded, a no-op on production- and dev-shaped databases. |

Not in migration 1: Module tables (S6) until the feature is in scope; any renaming of enum types
(S15); any change to `configBody`'s `json` type (S10, keep `json`).

## 3. Mapping the schema onto MikroORM

| Schema fact | MikroORM setting |
|---|---|
| Schema `main` | `schema: 'main'` in the ORM config (one place; the C++ has it in four). |
| Quoted camelCase identifiers (`"waferId"`, `"WaferType"`) | `namingStrategy: EntityCaseNamingStrategy` so property names are used as-is; `tableName` set explicitly on each entity to the PascalCase table name. Do **not** let the default underscore strategy run: `waferId` would become `wafer_id`. |
| `id integer GENERATED BY DEFAULT AS IDENTITY` | `@PrimaryKey({ autoincrement: true }) id!: number`. MikroORM's PG dialect declares new columns as `serial`; for existing identity columns that is only a DDL-diff concern, inserts behave identically. Keep migration 0 raw so the diff stays empty. |
| Native enum types (`main."wpGeneralLocation"`, …) | `@Enum({ items: () => WpGeneralLocation, nativeEnumName: 'wpGeneralLocation' })`. Keep the TS enums in `libs/epic/entities` (several already exist) and generate or cross-check them against `pg_enum`. |
| `json` columns (`waferMap`, `configBody`, `specification`, `local2GlobalMap`) | `@Property({ type: 'json' })` returns parsed objects; the wire format is a **string** ([01 §3](01-behaviour-decisions.md#3-handlers), R-7), so serialise with `JSON.stringify` in the reply mapper and parse on the way in. |
| `date` columns | `@Property({ type: 'date' })` as string `YYYY-MM-DD` (MikroORM `DateType`) to match today's wire format exactly. |
| `timestamp without time zone` on `SvtTestList` | `@Property({ type: 'timestamp' })`; the wire format decision is in [01 §3](01-behaviour-decisions.md#3-handlers) (R-6). |
| Composite primary keys (`AsicFamilyTypeBlockList`, `SvtTestSetupEquipList`, `SvtTestTypeDUTTypeList`, `ModuleChipList`, `ProbeCardFamilyType`) | `@PrimaryKey` on both properties or `[PrimaryKeyProp]`; or model them as pivot tables of `@ManyToMany` relations where that reads better (`SvtTestSetup.equipment`, `SvtTestType.dutTypes`). |
| `DEFERRABLE` foreign keys | `deferMode: DeferMode.INITIALLY_IMMEDIATE` on the relation, or leave unspecified and keep migration 0 raw. |
| Scalar "relations" the C++ merges (`SvtTestSetupDefaultConfig.defaultConfigId`, `SvtTestListToEntityName`, `SvtTestListToEntityId`) | `@OneToOne` / `@OneToMany` with `populate`, or a joined query in the repository. Return `null` when absent ([01 §1](01-behaviour-decisions.md#1-engine-level)). |
| Virtual columns from the C++ custom queries (`Asic.chipId`, `Chip.familyType`, `SvtTestTemplate.testTypeId`) | `@Formula` properties or explicit joins in the repository; they are reply fields, not columns. |

## 4. Enums: keep Postgres enums

The UI and the TestAgent depend on `GetAllEnums` reflecting the **live** catalog, and the
operational workflow today is "the DB owner runs `ALTER TYPE … ADD VALUE`". Keeping native enums
preserves that. The clone reads them from `pg_type` ⋈ `pg_enum` per request (or with a short TTL),
using `enumlabel` rows rather than parsing `enum_range()` text.

If the team later wants enum values managed through the UI, that is a new message type and a
migration to lookup tables; not part of the swap.

## 5. Timestamps and history ordering

History tables record `date` at day resolution and the C++ picks the current location by
`ORDER BY date DESC`. With surrogate ids (§2) the clone can order by `id`, which is unambiguous.
Moving history `date` to `timestamptz` is a separate, optional migration that changes the wire
format of `date` in history replies (`YYYY-MM-DD` today); decide it with the UI.

## 6. Transactions

Every handler runs in one `em.transactional()` block. The multi-statement handlers that are
non-atomic today are listed in
[04 §7](../../../DbAgent/docs/04-request-engine.md#7-transaction-semantics); after the swap a failed
`CreateWafer` leaves no wafer, no location row and no ASICs.

## 7. Connection and pool

One connection today; the clone uses the driver pool (default is fine). Requests become
concurrent, which is safe once ids come from `RETURNING` and writes are transactional. Keep
`statement_timeout` modest so a slow query cannot hold a transaction across a Kafka rebalance.
